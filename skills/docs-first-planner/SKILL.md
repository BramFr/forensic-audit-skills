# Docs-first planner

Vibe coding goes wrong in predictable ways: building on unverified beliefs about the code, adding features that duplicate or contradict earlier ones, losing track of why something exists, and drifting away from the product vision. This skill counters that by making every change pass through the same phases, keeping `./docs` as the single source of truth checked on every run, giving new modules a written contract before any code exists (scaffold), and reading everything in layers, summary first (progressive reading).

Write everything the user reads, and every file saved to `./docs`, in the language the user writes in. Folder names and frontmatter keys stay as specified below.

## The flow

```
0 Intake -> 1 Docs check -> 1.5 Dimension research -> 2 Forensic audit -> 2.5 First-principles analysis
  -> 3 Grill (3-10 questions) <-> 3.5 Verification loop (search again) -> 4 Plan (approval) -> 5 Persist
```

Phase 1.5 (first-principles dimension research, embedded directly from `../first-principles-architect/SKILL.md` / `skills/first-principles-architect/SKILL.md`) runs between phases 1 and 2.

Run phases 0-2.5 in one go without asking permission between them. Phases 3 and 3.5 repeat interactively until the verification loop is closed. **Never write to `./docs` before the user has approved the plan in phase 4** (except for the automatic outcome of a failed regression check). For software projects, this skill plans and does not implement the change (writing approved scaffold folders and `MODULE.md` contracts—no implementation code—is part of persisting the plan). For non-software systems (recipe, training protocol, physical/mechanical tuning or renovation), the fully quantified specification IS the plan saved in `./docs`.

### Shared Execution Rules (Canonical Reference)

All phases below share these canonical execution rules:

1. **Project `## Search keywords` Scoping, `auto_open_top` Compound Search & Batching (`<= 9.500 B` inline budget):**
   - Check `./docs/index.md` for `## Search keywords` first via `compress_context(file_path="docs/index.md", section="Search keywords")`.
   - When present and in the project's domain, include **1 to 3 matching keywords** per query (`{selected keywords} {query}`): pick **1–2 leading vision/scale priority terms** from the start of the list for architecture, UI, workflow or scale queries, or **1–2 technical/methodological domain terms** (`primary-source-verification`, `ISO-NEN-IEC`, `IETF-RFC`, `NIST-SP-800`, `OWASP-ASVS`, `Python-stdlib`) for external protocol, standard, RFC, library or scientific queries—never prepend abstract vision words like `zero-trust` or `no-fake-green` to external standard queries, strip `+` punctuation, and never send 0 keywords (`0` project keywords when `## Search keywords` is present = `🚫 NOT SEARCHED`). When absent or out of domain, search normally.
   - Prefer `search_website(query_or_url="...", auto_open_top=1)` or batch calls `search_website(queries_or_urls=[...], auto_open_top=1)` (or `"open: <query>"`, up to 10 items/call, backed by SQLite WAL + `ETag` caching and session-delta block re-slicing): keep DuckDuckGo queries concise at **4 to 6 core terms** (one language and one standard/concept per query). Using `auto_open_top=1` (or `open:`) runs search + authority-ranked primary URL opening in **1 turn** (`🔎 SOURCED`), or pass `search_website(query_or_url="https://...", filter_query="<keywords>")` to stay within the `<= 9.500 B` (`<= 10.240 B`) inline budget without mid-paragraph slicing. For paywalled standards (ISO/NEN/IEC), name the standard AND open its free **open primary counterpart** for `🔎 SOURCED`. An `ERROR:` response never counts as `🔎 SOURCED`.
2. **Complexity Switch (`3 to 6 sub-topics` + `4 lifecycle safeguards`) & Both Control Points (`2 pros and 2 cons from subject to solution`):**
   - Classify every wish in Phase 1.5 as **single-topic** (1 unit across D1–D7) or **composite** (a multi-stage end-to-end creation). Decompose composite wishes before searching into **3 to 6 sub-topics** plus **4 lifecycle safeguards**: (1) *Preparation and first-run readiness* (idempotent setup adapted to capacity), (2) *Handoff and scale continuity* (no truncation, drift or misgrouping as volume grows), (3) *Coexistence with the surrounding environment* (safe active load cap and no premature sleep or disruptive prompts), and (4) *Ongoing use, selective recovery and clean delivery* (re-running one adjusted/failed sub-topic without redoing earlier verified stages, and clean delivery).
   - Enforce **Control Point 1 (Research & Register)** and **Control Point 2 (Grill Options, Decisions & Plan Check)**: at both points, evaluate and record **2 pros and 2 cons from subject to solution**.
3. **Batch Prompting (`arXiv:2511.04108`), DAST/CoD Differentiation & Zero-Trust Context-Purge:**
   - Execute the 7 orthogonal D1–D7 layer searches (Phase 1.5) and 10 P1–P10 claim/component searches (Phase 2)—17 distinct queries with zero repetition—as a bundled research batch (**Batch Prompting**, without hard `"use at most X tokens"` caps) under a **Difficulty-Adaptive Budget (DAST)**: concise *Chain-of-Draft (CoD)* density for D1–D7 and full deep reasoning for P1–P10 and Step 2B disconfirmation.
   - Delegate the combined 7+10 web-research batch (after Phase 0 and Phase 1) to a single `research` or `self` subagent using `auto_open_top=1` that reads primary sources and performs a **Zero-Trust Context-Purge**, returning only the two clean `#schema:` tables (D1–D7 criteria register with Control Point 1 + P1–P10 audit table) and verified facts, after which the main agent continues in the same turn with Phases 2.5, 3, 3.5 and 4.
4. **Step 2B Adversarial Disconfirmation & Triple Actuality/Typology Check:**
   - Do not search only for confirmation (Step 2A). On uncertain assumptions, contested thresholds or legacy practices, run an active disconfirmation search (Step 2B: *has this standard, rule, method or specification been withdrawn, deprecated, superseded or refuted?*) and verify: (a) *Existence at time horizon $t$* (still in force), (b) *Typology* (strict binding outcome obligation vs. flexible guideline), and (c) *Higher authority* (not overruled by a higher jurisdiction or primary spec). On norm decay, trigger a fail-closed rollback.
5. **Simplicity Ladder & Cognitive Ergonomics (Hick's Law Smart Defaults + `<details>` Progressive Disclosure):**
   - Walk the **Simplicity Ladder** top-down on every design choice: (1) *Necessity (YAGNI)*, (2) *Reuse (DRY)*, (3) *Existing standard / built-in capabilities*, (4) *Native environmental safeguards*, (5) *Already chosen means*, (6) *Minimal custom addition* with early boundary checks (LBYL).
   - Offer **3 to 5 choices per decision point** with the pre-researched Smart Default first (`(Recommended)`), and wrap large supporting tables at the bottom in `<details><summary>...</summary></details>` blocks.
6. **3-Phase `compress_context` (Tiered `filter_query` + Slim Plan-Read) & Execution-Subagent Isolation (`mcp/context-compressor`):**
   - Use `compress_context` across all phases: (1) **Phase 1 & Skill Progressive Reading** (`filter_query="<wish keywords>"` on `docs/index.md` for tiered `#schema:` projection; default **slim plan-read** on `docs/<cat>/NN-slug.md` keeping 2-col `Decisions` + `Scope (Out)` and omitting heavy sections unless `section="Scope,Approach,Acceptance criteria"` or `--all`; section-scoping on `SKILL.md`/references for subagents), (2) **Phase 2 Subject/File Audit** (`section="--signatures"` or symbol/key selectors on structured files, and read-only `research` subagent Context Packs on `>= 3` files), and (3) **Phase 4/5 Execution-Subagent Isolation**: whenever any file or deliverable is written or modified, delegate the change to a fresh execution subagent (`invoke_subagent` / `Agent`) with a lossless **Subagent Context Pack** (`--signatures` + target sections/symbols + `MODULE.md`, Pipe-DSV `#schema:`, or `JSON_COMPACT`; no lossy word-pruning or parallel same-file edits).

### Phase 0: Intake

Take the user's wish (the text after the skill call). If it is empty, a placeholder, or too vague to name an area of the project or subject, ask one short question and stop. Make a first guess at the category (`bug`, `feature`, `refactor`, `chore`, `research`) and name the touched area.

**Security route.** If the wish is about security (scan, vulnerabilities, secrets, dependencies, hardening, access control, threat model, compliance, or a feature whose main risk is security), set the category to `security` and follow the security route (phases 2, 4 and 5; ask for scope in phase 3 if missing). A normal feature or bug touching security-sensitive areas stays on the normal route, using `forensic-security-audit` for security points in phase 2.

**Failure in the wish.** If the wish contains or describes a failure (error, log, failed check, or physical/procedural/domain failure), set the category to `bug`, keep the failure text verbatim (secrets masked), and diagnose it with the seven steps of `forensic-audit` Principle 6 and Shared Execution Rules 1, 4 and 5: (1) **Discover** domain, subject and jurisdiction, scope `## Search keywords`, and search live (`search_website` + Step 2B disconfirmation) for the signal and governing standard (law, ISO/NEN/IEC/RFC, regulator, primary docs, or guild guideline; opening the free **open primary counterpart** when a formal standard is paywalled for `🔎 SOURCED`), (2) **Quote** the signal, (3) find the decisive **Signal** at its origin, not the wrapper, (4) check whether it is a deliberate **Guard** (satisfy it, never remove it), (5) list at most 3 **Hypotheses** with a cheap test each, (6) propose the **Fix** as plan steps aligned with the source and Simplicity Ladder, (7) define how to **Confirm** it as a checkable acceptance criterion. The root cause is one of the 10 audit points in phase 2 (Impact), stating whether it is verified or still a hypothesis.

### Phase 1: Docs check (every invocation)

1. Read `./docs/index.md` via `compress_context(file_path="docs/index.md", section="Product vision,Standing constraints,Search keywords,Items,Modules", filter_query="<wish keywords>")` (tiered projection: `ID|Status|Title|Summary|Tags` for matches, `ID|Status|Title` for others). If `./docs` exists, run `python <skill-path>/scripts/docs_tool.py check` from the project root (`docs OK` means clean; problems are fixed in phase 5). Every item needs frontmatter keys `id`, `title`, `category`, `status` and `summary`.
2. **Read in layers (progressive reading & slim plan-read, Shared Execution Rule 6).** Open only the top related items: an unfiltered `compress_context(file_path="docs/<cat>/NN-slug.md")` returns a **slim plan-read** by default (frontmatter + `Why` + 2-col `Decisions` + `Scope (Out)` + `Risks` + `Relations`, omitting `Starting point`, `Decisions (Reason)`, `Scope (In)`, `Approach`, `Acceptance criteria` and `Verification`; load heavy sections via `section="Scope,Approach,Acceptance criteria"` or `--all`). In a git repo, check recent `git log`/`git diff` of touched folders first.
3. Produce a short **docs match** result: **Vision & Standing constraints fit** (Fits / Partial / Conflicts / Unknown + one line of reasoning), **Related items** (ID, status, relation: duplicate, overlaps, depends on, superseded), and **Stale or contradictory items**. If `./docs` or `index.md` does not exist, note that it will be created after approval (asking for the vision in phase 3).
4. **Regression check (before).** For related `done` or `in-progress` items (and `./docs/security/` if present), load `section="Acceptance criteria"` and run their `Check:` lines under "Regression check rules", reporting passed, failed, manual, needs approval or could not run. Failed or stale checks go under **Stale or contradictory items** and into the grill. When **Vision fit is Conflicts** or the wish duplicates an existing item, make that the first grill question.

### Phase 1.5: First-principles dimension research (every wish, every route)

Read `../first-principles-architect/SKILL.md` (`skills/first-principles-architect/SKILL.md`, via `compress_context` `section="Phase 0: Principles research (always, whatever the request)"`): it is the single canonical source for the embedded `first-principles-architect` skill. Translate every query and question into the vocabulary of the wish without carrying terms or numbers over from another subject.

Run its Phase 0, steps 1 to 3, now and **before the forensic audit**, following `### Shared Execution Rules` (1–4):
1. **Complexity switch:** Classify the subject as **single-topic** or **composite** (**3 to 6 sub-topics** + **4 lifecycle safeguards** per Shared Execution Rule 2).
2. **Research D1 to D7, run Step 2B disconfirmation, and record Control Point 1 (`2 pros and 2 cons from subject to solution`):** Research each of the 7 dimensions (baseline, target, hard constraints, failure modes, system dynamics, resource budget, reversibility) with **at least one live search per dimension** (official sources only; `⚠️ NO SOURCE FOUND` when missing; show conflicts explicitly) and maintain the internal criteria register (`dimension_or_subtopic | criterion | 2 pros & 2 cons (from subject to solution) | measurable threshold or test | official source + status label`). Delegate the combined Phase 1.5 (7 D1–D7 CoD searches) + Phase 2 (10 P1–P10 deep-reasoning searches) batch (`auto_open_top=1`) to a `research`/`self` subagent with a **Zero-Trust Context-Purge** returning both `#schema:` tables (Shared Execution Rule 3), then continue in the same turn with Phases 2.5, 3, 3.5 and 4.

### Phase 2: Forensic audit of the project

Use `forensic-audit` in COMPACT mode (`compress_context` `section="Principles,Pre-build use (principles research)"`) on the **current state of the project or subject around the wish** (touched files/parameters via Shared Execution Rule 6, claims in `./docs`, and hidden assumptions in the wish).

- **Principles of the wish & orthogonal 7 + 10 searches (17 unique queries, zero duplicates):** Use `forensic-audit` in pre-build mode on the **wish itself**. Whereas Phase 1.5's 7 dimension searches (D1–D7) ask layer-specific questions, Phase 2's 10 audit-point searches (P1–P10) test 10 concrete claims, components, parameters and edge cases of the wish and project state—always producing **different search queries and different results**. Begin from the phase 1.5 register, add what its searches missed, verify **Control Point 1 (`2 pros and 2 cons from subject to solution`)**, challenge weak/superseded sources (Step 2B), and read `references/audit-brief.md` for selecting P1–P10, evidence rules, module boundary checks and plan mapping. **The external source search is mandatory** for every point (`🚫 NOT SEARCHED` if skipped).
- **Security route:** Use `forensic-security-audit` (phases 1 to 3 in COMPACT mode; merge Phase 0 questions into grill rounds; record fixes as plan steps, masking secrets everywhere).
- **Fix discipline for bugs, issues and failures (every route):** (1) **Reproduce first** (failing check/test or reproduction step), (2) **Root cause** (underlying cause vs. missing structural guard), (3) **Blast radius** (search the **whole project** for the pattern and report count + locations; raise a grill question if >10 places), (4) **Smallest safe change, applied project-wide** (Simplicity Ladder top-down, one central fix over local patches), and (5) **Guard and opposite test** (lasting guard + opposite test proving original failure gone, 0 pattern hits, and guard rejects bad input).
- **Hand-over to the grill (do not stop here, keep Phase 2.5 silent in chat):** Show only a brief audit summary (verdict, what was wrong, unverified/source gaps, `docs_tool.py check` problems, tools line; wrap large tables in `<details><summary>...</summary></details>`). Keep Phase 2.5 (D1–D7 overview and 8-part analysis) strictly internal to drive the grill—do NOT print D1–D7 in chat unless asked for the "full report". In the **same turn**, run phase 2.5 and continue straight into phase 3, ending with the first round of grill questions in plain text.

### Phase 2.5: First-principles analysis

Read `references/first-principles.md` (phase 2.5 section). Map the wish and audit findings onto D1–D7 (plus the 3 to 6 sub-topics and 4 lifecycle safeguards when composite), correct wrong assumptions with their source, apply the **Pre-Grill Invariant Gate** (filter out any option violating `## Standing constraints`, `MODULE.md` `Does NOT do` or prior `## Decisions` / `Out:`), walk the **Simplicity Ladder** (Shared Execution Rule 5), and draft the 8-part system analysis of `../first-principles-architect/SKILL.md` (Phase 2, including part 5: perception, cognition and sensory ergonomics) internally without printing D1–D7 in chat. Never guess a missing parameter; every gap becomes a grill question or research item.

### Phase 3: Grill

Interview the user until the plan is unambiguous (`grill-me` skill or this protocol), enforcing the **Pre-Grill Invariant Gate** (never propose or mark `(Recommended)` an option contradicting `## Standing constraints`, boundary exclusions or prior `## Decisions`/`Out:`; if the user's wish conflicts with a standing constraint, ask as question 1 whether to supersede it). **You are the lead specialist/architect, the user is not:** work out options yourself and ask only what the user can judge in plain language:
1. The situation in one sentence, in the user's terms.
2. **3 to 5 options (Hick's Law)** with practical impact (effort, cost, risk), explaining any specialist term briefly the first time.
3. Your pre-researched Smart Default first, marked "(Recommended)", with a one-line reason and **Control Point 2 (`2 pros and 2 cons from subject to solution`)**, plus "or tell me to decide".

- **Ask 3 to 10 questions per plan, in rounds of 3 to 5 (or 1 round of 4 to 6 questions for composite wishes covering the 3 to 6 sub-topics and 4 lifecycle safeguards).** Target the highest-leverage missing/assumed dimensions from phase 2.5 (`references/first-principles.md`, "Grill rules"), ordering questions: (a) audit verdict/scope blockers, (b) phase 1 vision/constraint conflicts or duplicates, (c) missing dimensions. Always write questions and options as plain text at the end of the message. Stop after 10 questions and mark remaining gaps unverified, unless the user asks for more.
- Look up anything answerable from existing materials, docs or primary sources instead of asking. Walk the decision tree depth first: problem/outcome -> vision fit -> scope in/out -> unfixed choices -> boundaries/interfaces -> edge cases -> acceptance criteria -> priority. Ask for a 3–5 line product vision if missing in `index.md`, and use remaining questions (if <3 gaps exist) to confirm the riskiest assumption (D4, D7, lifecycle safeguard, or phase 2.5 misconception).

### Phase 3.5: Verification loop (after every round of answers)

Check the user's answers as new claims (`references/first-principles.md`, "Phase 3.5"):
1. **Search again (with Step 2B disconfirmation)** using `search_website` (`auto_open_top=1`, Shared Execution Rules 1 and 4) for every answer setting a parameter, limit, target or method, plus any newly implied sub-parameter or constraint.
2. **Confidence gate & Circuit breaker.** A causal-chain link passes only on a `🔎 SOURCED` primary source, reproduced test or actual measurement. On a parameter mismatch, confidence gap, Step 2B norm decay, or collision with D3/D6: repair the chain and ask a follow-up round if needed (within the 10-question limit). On an irreconcilable deadlock, stop, name the blockage with its source, and propose adjusted boundary conditions.
3. Proceed to phase 4 only when every link passes the gate or is marked unverified and no circuit breaker is open. **Re-audit trigger:** if an answer changes scope, approach, dependencies or assumptions, re-audit the changed claims in this loop.

### Phase 4: Plan and approval

Prepare the plan structure from `references/plan-template.md` (adding `references/scaffold-template.md` when creating/reshaping modules, or `references/security-plan-template.md` on the security route) and run the **plan check** (`references/first-principles.md`, "Plan check additions"):
- Every acceptance criterion is checkable (`Check:` command, test or observable measurement), "Out (explicitly not doing)" is filled in, unverified claims are marked, and every step passed the **Simplicity Ladder** (Shared Execution Rule 5).
- Every phase 2/re-audit finding and applicable principles-register criterion appears in a step, decision, risk or acceptance criterion with its source; bugs include reproduction, root cause, project-wide blast radius, lasting guard and opposite test; all 7 dimensions, **3 to 6 sub-topics**, **4 lifecycle safeguards**, **Control Point 1** and **Control Point 2** (`2 pros and 2 cons from subject to solution`), non-overlapping boundaries, confidence gate + Step 2B checks, and high-stakes `🟡` Impact confirmations are satisfied.

**Slim Phase-4 chat presentation (do NOT dump heavy plan sections in chat):** Show **only a concise plain-language summary in chat** (proposed `id`/`title`/`summary`, `## Why`, compact overview of agreed decisions & approach, and `## Risks and open points`). **Do NOT write out the full heavy Markdown sections (`## Starting point`, `## Decisions`, `## Scope`, `## Approach`, `## Acceptance criteria`) in chat** unless explicitly requested; they are written to `./docs/<category>/NN-slug.md` in Phase 5 after approval. Ask explicitly for approval ("akkoord", "approved", "go").

### Phase 5: Persist (only after approval)

**Never write to `./docs` before user approval in Phase 4.** Once approved (`"akkoord"`, `"approved"`, `"go"`), load and execute `compress_context(file_path="skills/docs-first-planner/references/persist-and-regression.md", section="Phase 5: Persist (only after approval)")`: run `docs_tool.py next <category>`, save the full plan to `./docs/<category>/NN-short-slug.md`, update bidirectional `related` links, `superseded` statuses, synchronous prose in refined items, product vision, `## Standing constraints` and `## Search keywords` in `index.md`, write/merge `MODULE.md` contracts (`docs_tool.py modules`), run `docs_tool.py index` and `check` (plus `./docs/security/NN-security-baseline.md` on the security route), run the **Regression check (after)**, and report the saved path, index row and first step.

## Later invocations & Regression check rules

For status updates (`planned`, `in-progress`, `done`, `dropped`, `superseded`) and **Regression check** execution (Phase 1, Phase 5, and before marking `done`), load and follow `compress_context(file_path="skills/docs-first-planner/references/persist-and-regression.md", section="Later invocations: status updates,Regression check rules")`: check only related `done`/`in-progress` items plus `./docs/security/` (loading `section="Acceptance criteria"`), running read-only local `Check:` commands automatically and marking state-changing/network commands `needs approval`. On a failed check, set `status` to `in-progress`, log the masked failure under `## Verification`, create `./docs/bugs/NN-regressie-<slug>.md` with bidirectional `related` links, and run `docs_tool.py index` and `check`.

## Guardrails

- Docs are hypotheses until tests/measurements confirm them; do not invent goals; keep index rows to one line.
- **A fix is not `done` while the pattern remains elsewhere:** re-verify 0 blast-radius hits and guard failure on reintroduction under `## Verification`.
- **No brute force around a missing contract:** update the plan or `MODULE.md` before adding boundaries; keep contracts short and layered.
- **Subagent Isolation & Context Pack Protocol:** do not execute after plan approval unless asked; when executing, follow Shared Execution Rule 6 (`compress_context` across Phases 1, 2 and 4/5, delegating every file modification to a fresh execution subagent).
- **Security route:** verify `done` security items with `forensic-security-audit` re-tests, confirm secret rotation with the user, and check `./docs/security/` in phase 1 of every later plan.
